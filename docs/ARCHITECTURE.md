# Architecture

PitFlow은 Next.js Frontend, Spring Boot Backend, PostgreSQL Database로 구성됩니다.

## 전체 구조

```text
Browser
   ↓
Next.js
   ↓
Spring Boot
   ↓
PostgreSQL
```

배포 환경:

```text
Vercel
  ↓
Render
  ↓
Neon PostgreSQL
```

결제 시 Backend가 Toss Payments API와 통신합니다.

## Backend 영역

```text
auth          로그인 / 권한
appointment   예약
catalog       정비 서비스
mechanic      정비사
work          입고 / 정비 작업 / 재고 사용
billing       정산 / 수납 / Toss 결제
finance       원가 / 매출 / 회사 자금
notification  업무 알림
```

## 사용자 역할

### CUSTOMER

본인 차량, 예약, 정비 이력과 결제만 접근할 수 있습니다.

### MECHANIC

본인에게 배정된 정비 작업을 진행하고 부품 사용·반환 및 작업 완료를 처리합니다.

### ADMIN

예약 확인, 입고, 정비사 배정, 재고, 정산, 결제, 환불, 출고와 재무 정보를 관리합니다.

권한 검사는 Frontend가 아니라 Backend에서 최종 수행합니다.

인증은 서버 세션과 CSRF 보호를 사용합니다. 요청마다 계정 식별자, 현재 권한·활성 상태와 로그인 당시 자격 증명을 대조해 변경 전 세션을 무효화합니다.

## 데이터 처리 원칙

### 과거 기록

예약이나 정비가 끝난 뒤 서비스 가격이 변경되어도 과거 기록은 바뀌지 않습니다.

필요한 이름, 가격과 작업시간을 당시 값으로 별도 저장합니다.

### 재고

재고는 실제 입고, 사용, 반환, 수정이 있을 때만 변경합니다.

부품 부족 신고 자체는 재고를 바꾸지 않습니다.

작업 배정, 완료, 부품 부족과 해결 알림은 수신자별로 저장하며 업무 변경과 같은 트랜잭션에서 처리합니다.

### 부품 원가

판매 가격과 실제 구매 가격을 분리합니다.

먼저 입고된 재고부터 사용하는 FIFO 방식으로 실제 사용 원가를 계산합니다.

구매 가격을 알 수 없는 기존 재고는 임의로 0원 처리하지 않습니다.

### 결제

결제 가능 여부는 현재 남은 결제 금액으로 판단합니다.

환불된 Toss 주문은 기록으로 남기고 재결제에는 새로운 주문을 생성합니다.

현금이나 계좌이체로 다시 결제할 수도 있습니다.

### 회사 자금

고객 결제, 환불, 부품 구매, 운영비와 급여 지급이 회사 자금 변화에 연결됩니다.

이전 기록을 수정해서 없애기보다 새로운 변경 기록을 추가해 과거 흐름을 확인할 수 있게 했습니다.

## 동시 요청 처리

예약, 재고, 결제처럼 동시에 실행되면 문제가 생길 수 있는 기능은 Database 잠금과 중복 요청 방지를 사용합니다.

최종 금액과 수량은 처리 직전에 서버에서 다시 확인합니다.

## Database 변경

Database 구조는 Flyway로 관리합니다.

이미 적용된 migration 파일은 수정하지 않고 새로운 변경이 필요한 경우 다음 버전을 추가합니다.
