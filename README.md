# PitFlow

자동차 정비소의 **예약 → 입고 → 정비 → 부품 사용 → 정산 → 결제 → 출고** 흐름을 한 곳에서 관리하기 위해 만든 웹 서비스입니다.

고객, 정비사, 관리자가 서로 다른 화면과 권한을 사용하고, 예약 이후 실제 정비 업무가 끊기지 않고 이어지도록 구현했습니다.

## 구현에서 신경 쓴 부분

### 과거 예약과 정산 금액 보존

서비스 가격은 나중에 바뀔 수 있지만 이미 예약했거나 정비가 끝난 기록까지 같이 바뀌면 안 된다고 판단했습니다.

그래서 예약·정비 시점의 서비스 이름, 가격, 수량을 별도로 저장해 과거 기록이 현재 서비스 정보의 영향을 받지 않도록 했습니다.

### 실제 움직인 재고만 반영

정비에 필요한 부품 목록과 실제로 사용한 부품은 다를 수 있습니다.

부품이 필요하다는 이유만으로 재고를 미리 차감하지 않고, 실제 사용 시 차감하고 반환 시 다시 복구하도록 했습니다.

구매 원가는 판매 가격과 따로 관리하고, 서로 다른 가격으로 입고된 재고는 먼저 들어온 재고부터 사용하는 FIFO 방식으로 계산합니다.

### 서버에서 최종 상태 확인

결제 금액, 재고 수량, 사용자 권한처럼 중요한 값은 화면에서 넘어온 값을 그대로 사용하지 않습니다.

예약·재고·결제처럼 동시에 여러 요청이 들어올 수 있는 기능은 처리 직전에 DB 상태를 다시 확인하고, 필요한 곳에는 잠금과 중복 요청 방지 로직을 적용했습니다.

### 역할과 세션 분리

고객은 본인 차량과 이력만, 정비사는 본인에게 배정된 작업만 접근할 수 있도록 Backend에서 권한을 확인합니다.

계정이 비활성화되거나 비밀번호·이메일 같은 인증 정보가 바뀐 경우에는 기존 로그인 세션이 계속 사용되지 않도록 세션 검증도 추가했습니다.

### 업무 알림과 일반 메시지 구분

단순 저장 성공은 Toast로 보여주고, 부품 부족 신고나 해결처럼 나중에 다시 확인해야 하는 업무는 Notification으로 저장합니다.

정비사가 부족 신고를 올리면 관리자에게 전달되고, 관리자가 해결하면 현재 담당 정비사에게 다시 알림이 가도록 연결했습니다.

## 트러블슈팅

### 1. Toss 환불 후 같은 정산 건을 다시 결제할 수 없던 문제

처음에는 하나의 정산 명세에 하나의 Toss 주문만 연결하는 구조였습니다.

결제 자체는 정상적으로 됐지만 전액 환불 후 같은 정산 건을 다시 결제하려고 하면 기존 주문번호가 남아 있어 이미 처리된 주문으로 판단되는 문제가 생겼습니다.

단순히 기존 결제 정보를 덮어쓰는 방식은 환불 이력이 사라지고, 반대로 기존 주문번호를 그대로 재사용하면 Toss 쪽에서 재결제를 받을 수 없었습니다.

그래서 정산 명세와 결제 시도를 분리했습니다.

- 환불된 주문은 그대로 이력으로 보존
- 재결제 시 새로운 주문번호 생성
- 하나의 정산 명세에 여러 번의 결제 시도 기록 가능
- Toss 재결제뿐 아니라 환불 후 현금·카드·계좌이체 수납도 가능

최종적으로 다음 흐름을 모두 테스트했습니다.

```text
Toss 결제 → 전액 환불 → Toss 재결제
Toss 결제 → 전액 환불 → 현장 결제
```

### 2. 정비사 화면에서 필요한 추천 부품이 보이지 않던 문제

서비스별로 필요한 부품 정보는 이미 등록되어 있었지만, 실제 정비사가 작업 상세 화면을 열었을 때 추천 부품 목록이 내려오지 않는 문제가 있었습니다.

관리자용 상세 응답에는 관련 정보가 있었지만 정비사용 응답을 따로 정리하는 과정에서 필요한 필드까지 빠진 것이 원인이었습니다.

정비사에게 관리자용 재고 정보 전체를 그대로 노출하는 것도 맞지 않았기 때문에 응답을 단순히 공유하지 않고, 정비사에게 필요한 값만 따로 조회하도록 수정했습니다.

정비사 응답에는 다음 정보만 전달합니다.

- 부품 ID
- 부품명
- 단위

반대로 창고 수량, 판매가, 안전재고처럼 정비사 업무에 필요하지 않은 내부 정보는 노출하지 않았습니다.

이후 테스트에서 정비사는 본인에게 배정된 작업의 추천 부품만 볼 수 있고, 다른 정비사의 작업이나 관리자 전용 정보는 볼 수 없는지 함께 확인했습니다.

### 3. 계정을 비활성화하거나 비밀번호를 바꿔도 기존 세션이 살아 있던 문제

최종 코드 검토 과정에서 로그인한 사용자의 계정을 비활성화하거나 비밀번호를 재설정해도 이미 발급된 세션이 그대로 남아 있는 경우를 발견했습니다.

로그인할 때는 계정 상태를 확인했지만, 로그인 이후 요청에서는 세션에 들어 있는 인증 정보를 계속 신뢰하고 있었기 때문입니다.

특히 이메일이 변경된 뒤 이전 이메일이 다른 계정에서 다시 사용될 경우에는 오래된 세션이 잘못된 계정과 연결될 가능성도 있었습니다.

그래서 인증된 요청마다 현재 DB의 계정 상태와 로그인 당시 정보를 다시 비교하도록 수정했습니다.

확인하는 값은 계정 ID, 이메일, 역할, 활성 상태, 로그인 당시 비밀번호 정보입니다.

이 중 하나라도 달라지면 기존 세션을 더 이상 사용하지 못하도록 처리했습니다.

이 문제는 회귀 테스트 3개를 추가해 수정 전 실패를 재현한 뒤 수정했고, 전체 Backend 테스트까지 다시 실행해 확인했습니다.

### 4. 정비사 시급이 바뀌면 과거 작업 원가까지 달라질 수 있던 문제

정비사별 시급을 관리하는 기능을 추가하면서, 완료된 작업의 인건비를 현재 시급으로 다시 계산하면 과거 수익이 계속 바뀌는 문제가 생길 수 있었습니다.

예를 들어 작업 당시 시급이 20,000원이었는데 이후 25,000원으로 수정하면, 과거 작업까지 25,000원 기준으로 계산되는 식입니다.

과거 작업의 수익과 원가가 현재 설정값에 따라 달라지는 건 맞지 않다고 보고, 작업 완료 시점에 인건비 계산에 필요한 값을 따로 저장하도록 바꿨습니다.

저장하는 값은 작업시간, 당시 정비사 시급, 계산된 인건비입니다.

시급 정보가 없는 정비사는 임의로 0원 처리하지 않고 원가 미확정 상태로 남겨, 재무 화면에서 원가가 확정된 작업과 섞이지 않도록 했습니다.

이렇게 바꾼 뒤에는 정비사 시급을 나중에 수정해도 이미 끝난 작업의 인건비와 수익 계산은 그대로 유지됩니다.

## 아쉬운 점

모바일에서도 주요 기능은 사용할 수 있도록 반응형으로 만들었지만, 재고·정비 작업·재무처럼 한 화면에 정보가 많이 필요한 관리 기능은 작은 화면에서 가독성이 떨어집니다.

현재는 기능을 더 늘리기보다 v1.0.0에서 마무리했고, 다시 개선한다면 데스크톱 화면을 그대로 줄이는 방식보다 모바일에서 먼저 봐야 할 정보와 행동을 다시 정리하는 쪽으로 접근할 생각입니다.

## 로컬 실행

필요 환경:

- Java 17
- Node.js
- Docker Desktop

```powershell
cd "$env:USERPROFILE\Desktop\pitflow"

Copy-Item .env.example .env
docker compose up -d --build
```

실행 후:

```text
http://localhost:3000
```

실제 비밀번호와 API Key는 `.env`에서 관리하며 Git에는 포함하지 않습니다.
