# PitFlow

자동차 정비 예약부터 입고, 정비 작업, 부품 재고, 결제, 출고까지 연결한 정비소 운영 관리 시스템입니다.

고객·정비사·관리자가 각각 필요한 기능을 사용할 수 있고, 예약 이후의 실제 정비소 업무가 하나의 흐름으로 이어지도록 구현했습니다.

## 바로 보기

- Frontend: https://pitflow-orcin.vercel.app/
- Backend: https://pitflow-api.onrender.com
- Database: Neon PostgreSQL

Render 무료 환경을 사용하고 있어 오랫동안 접속이 없었던 경우 첫 요청이 다소 느릴 수 있습니다.

Toss Payments는 실제 결제가 발생하지 않는 테스트 환경을 사용합니다.

## 로컬 실행

필요 환경:

- Java 17
- Node.js
- Docker Desktop

```powershell
cd "$env:USERPROFILE\Desktop\pitflow"

Copy-Item .env.example .env
docker compose up -d --build
```

실행 후:

```text
http://localhost:3000
```

실제 비밀번호와 API Key는 `.env`에 설정하며 Git에는 포함하지 않습니다.

## 주요 기능

### 고객

- 회원가입 및 로그인
- 차량 등록 및 관리
- 정비 서비스와 예상 금액 확인
- 정비 예약 및 취소
- 정비 이력 확인
- 미결제 금액 확인
- Toss Payments 테스트 결제

### 관리자

- 예약 확인 및 차량 입고
- 정비사 배정과 재배정
- 휴무일 및 특별 영업일 관리
- 정비 진행 상태 확인
- 부품 및 재고 관리
- 부품 부족 신고 확인
- 정산 명세 발행
- Toss 결제 및 현장 수납
- 결제 환불 및 수납 취소
- 차량 출고
- 매출, 비용, 회사 자금 현황 확인

### 정비사

- 본인에게 배정된 작업 확인
- 정비 항목별 상태 관리
- 부품 사용 및 반환
- 부품 부족 신고
- 작업 완료

정비사는 정비 완료까지만 담당하고, 결제와 차량 출고는 관리자가 처리합니다.

### 부품과 재고

- 부품 등록, 수정, 삭제 및 복원
- 부품 입고와 재고 수정
- 실제 사용 부품 차감
- 반환 부품 복구
- 음수 재고 방지
- 실제 구매 가격과 고객 판매 가격 분리
- 먼저 입고된 부품의 구매 가격부터 사용하는 FIFO 방식
- 구매 가격을 알 수 없는 기존 재고 별도 관리
- 기존 재고 구매 가격의 전체·부분 확정

### 정산과 결제

- 정비 당시 공임과 실제 사용 부품으로 정산
- 현금, 카드, 계좌이체 현장 수납
- Toss Payments 테스트 결제
- 결제 취소 및 전액 환불
- 환불 후 Toss 또는 다른 결제수단으로 재결제
- 같은 요청이 반복되어도 중복 결제·환불 방지
- 미결제 금액이 있으면 차량 출고 차단

### 회사 자금

- 운영자금, 예금, 투자자산 관리
- 고객 결제와 환불 반영
- 부품 구매와 재고자산 연결
- 미결제 금액 관리
- 예금 이자와 투자자산 변동 반영
- 매출, 부품 원가, 인건비, 운영비 확인

법정 회계 프로그램이 아니라 정비소 운영 상황을 확인하기 위한 관리 기능입니다.

## 업무 흐름

```text
고객 예약
    ↓
관리자 차량 입고
    ↓
정비사 배정
    ↓
정비 작업
    ↓
부품 사용 / 반환
    ↓
정비 완료
    ↓
관리자 정산 명세 발행
    ↓
고객 또는 관리자 결제
    ↓
관리자 차량 출고
    ↓
고객 정비 이력
```

## 구현하면서 중요하게 본 부분

### 과거 가격 보존

정비 서비스 가격이 바뀌더라도 과거 예약이나 정산 금액이 같이 바뀌면 안 됩니다.

예약·정비·정산 당시의 이름과 가격을 별도로 저장해 과거 기록을 유지했습니다.

### 실제 움직인 재고만 변경

부품이 필요하다는 이유만으로 재고를 먼저 차감하지 않습니다.

실제 입고, 사용, 반환, 재고 수정이 발생했을 때만 수량을 변경합니다.

### 판매 가격과 구매 가격 분리

고객에게 청구하는 가격과 정비소가 실제로 구매한 가격을 따로 관리합니다.

부품 사용 원가는 먼저 입고된 재고부터 사용하는 방식으로 계산합니다.

### 중요한 값은 서버에서 확인

결제 금액, 사용자 권한, 재고 수량처럼 중요한 값은 화면에서 전달된 값을 그대로 사용하지 않습니다.

서버에서 현재 DB 상태를 다시 확인한 뒤 처리합니다.

### 중복 요청 방지

결제나 환불 도중 새로고침이나 네트워크 재시도가 발생할 수 있습니다.

같은 요청이 여러 번 들어와도 실제 결제·환불·재고 변경은 한 번만 처리되도록 구성했습니다.

## Troubleshooting

### Toss 결제창이 열리지 않던 문제

**문제**

결제 준비는 성공했지만 Toss 결제창이 열리지 않았습니다.

**원인**

현재 구현 방식과 맞지 않는 종류의 테스트 클라이언트 키를 사용하고 있었습니다.

**해결**

Toss SDK 오류를 확인하고 API 개별 연동용 테스트 키로 변경했습니다.

**결과**

결제 승인과 환불까지 정상 동작했습니다.

### 환불한 결제를 다시 결제할 수 없던 문제

**문제**

Toss 결제를 전액 환불한 뒤 같은 정산 명세를 다시 결제하면 이미 처리된 주문이라는 오류가 발생했습니다.

**원인**

DB가 하나의 정산 명세에 Toss 결제 주문 하나만 저장할 수 있게 되어 있어 취소된 주문번호가 다시 사용됐습니다.

**해결**

한 정산 명세에 여러 결제 시도를 기록할 수 있게 변경했습니다.

취소된 주문은 그대로 보존하고 재결제 시 새로운 주문번호를 생성합니다.

**결과**

Toss 결제 → 환불 → Toss 재결제와 Toss 결제 → 환불 → 현금 재결제를 모두 지원합니다.

### 기존 재고의 구매 가격을 알 수 없던 문제

**문제**

일부 기존 재고는 수량은 있지만 실제 구매 가격 기록이 없었습니다.

0원으로 계산하면 재고자산이 실제보다 작게 표시됩니다.

**해결**

구매 가격이 확인되지 않은 재고를 별도로 표시하고, 관리자가 확인한 수량만 나중에 가격을 확정할 수 있게 했습니다.

과거 재고 가격을 확인하는 작업은 새로운 구매가 아니므로 회사 자금을 다시 차감하지 않습니다.

### 전체 테스트에서만 일부 테스트가 실패한 문제

**문제**

각각 실행하면 정상인 테스트가 전체 테스트 실행에서만 실패했습니다.

**원인**

일부 테스트가 공용 테스트 DB의 부품 데이터를 삭제했고, 뒤에서 실행되는 테스트가 해당 데이터가 계속 존재한다고 가정했습니다.

**해결**

각 테스트가 자신에게 필요한 데이터를 직접 준비하도록 변경했습니다.

**결과**

테스트 실행 순서와 관계없이 동일하게 동작하도록 정리했습니다.
